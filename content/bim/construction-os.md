## 三层产品栈

Construction OS 是一个三层产品栈，试图回答同一个问题：**如何让施工计划成为一个活的、可验证的数字孪生，而不是一份画完就过时的静态文档？**

```
3D 工作台（视觉决策层）
    ↑
aedile 引擎（数字孪生维护层）
    ↑
CPML 编译器（计划验证层）
```

每层有明确的职责边界，下层不感知上层。

## 第一层：CPML 编译器

计划验证。回答：**这个计划本身有没有冲突？**

声明式 DSL → 六阶段编译管线 → 碰撞/争用/漂移诊断。编译到 WASM 支持浏览器内分发。独立可运行，不依赖上层。

## 第二层：aedile 引擎

数字孪生维护。回答：**计划和现实之间的偏差有多大？**

aedile 读取 CPML 计划文件和现场数据，构建统一的内存模型，调用 `cpml check` 做基础诊断，然后生成结构化报告——进度偏差、成本偏差、风险热力、挣值分析、审计追踪。

但 aedile 的核心设计不是报告生成——是 **Agent 化的数字孪生维护**。它有完整的领域模型：

- **Project**：项目元信息
- **CpmVersion**：计划的版本——每次计划调整产生一个新版本，可 diff
- **ActivityState**：每个施工活动的当前状态——不是"完成/未完成"，而是更细粒度的 WBS 状态机
- **WorkOrder**：施工指令——谁、在哪里、做什么、验收标准
- **Issue**：异常事件——事故、延迟、质量问题
- **Change**：变更请求——设计变更、计划调整
- **Survey**：现场测量数据
- **Equipment**：设备——含里程碑（排产/发货/到货/安装/验收）

6 个自动化 Agent 负责跨实体数据传导：

- 工单完成后 → 自动更新活动状态
- 设备延迟到货 → 自动评估对关联活动的风险，生成预警
- Issue 被标记为"影响进度" → 自动生成变更请求
- 现场测量数据与计划对比 → 自动标记偏差

Agent 之间通过标准化事件解耦。每个 Agent 只关注自己的实体类型，不需要理解全局。这和 Agent Harness 的控制切面设计是一致的——aedile 本身就是 Agent 架构在施工领域的具体实例化。

技术栈：Python（约 5,600 行），FastAPI + 8 个 REST 路由器，SQLAlchemy/Alembic 持久化，Typer CLI 10 个命令组。

## 第三层：3D 工作台

视觉决策。回答：**我现在看到了什么？我应该关注哪里？**

React + TypeScript + Three.js（约 1,200 行）。加载 CPML 编译产物和 aedile 状态数据，渲染：

- 施工几何体——按活动状态着色（计划/进行中/延迟/完成）
- 诊断信息叠加——碰撞点高亮、资源争用区域标注
- 时间线控件——拖动时间轴观察施工过程演进
- 可拖拽多面板——暗色/亮色主题，ACES 色调映射

## 产品现状

CPML 功能完整。aedile 领域模型扎实但部分集成功能待完成（报告格式化、飞书适配、WebSocket 推送）。3D 工作台已搭建基础框架。

三个组件的设计文档、技术债务记录和教程在 [GitHub](https://github.com/IndenScale/construction-os) 上。

## 产品逻辑

Construction OS 不是"施工管理的数字化"。数字化是把纸质的变成电子的——甘特图变成 Project 文件，Excel 变成在线表格。这是在同一个范式里换介质。

一个操作系统的工作是**管理资源、调度任务、隔离故障、提供可观测性**。在施工现场：
- 资源 = 空间、设备、材料、人力
- 任务 = 施工活动
- 故障隔离 = 一个区段的问题不应该阻塞整个项目
- 可观测性 = 随时知道每个活动在哪个状态、偏差多大、风险在哪

这才是"施工操作系统"的含义——不是工具集合，是**资源管理和执行调度的运行时**。
