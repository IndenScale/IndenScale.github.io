Engineering as Code：为何AI还无法胜任工程设计？
——一场关于大模型能力边界的深度思辨

大语言模型能写诗、能生成代码、甚至能上线一个完整的网站。在芯片和PCB设计这类“硬件工程”领域，AI的表现也可圈可点。然而，当我们转向更传统的工程设计——建筑、桥梁、机械、水利——AI却显得举步维艰。这究竟是为什么？

在过去的一段时间里，我与多位工程师和研究者进行了一场层层递进的深度对话。最初，我试图用“物理直觉的缺失”“硬约束求解的困难”“反馈周期过长”来解释。但这些论点，都在对方一次次精准的追问下土崩瓦解。

直到一个更具根本性的概念被提出，真相才终于浮出水面：“Circuit as Code”的缺失，以及由此导致的质量保证体系的“左移”断层。

一、不断被推翻的解释
对话刚开始，我的论点看似合理：

AI不懂物理因果：它只能做统计关联，无法像工程师那样进行反事实推理。

工程设计是硬约束求解：材料强度、安全法规是硬边界，AI的概率生成与之相悖。

隐性知识无法学习：资深工程师的直觉和经验从未被文字记录。

但反驳来得既快又准：一个能在真实服务器上、通过编译测试、最终成功上线的AI智能体，怎么可能不懂因果，不处理硬约束？ 编程同样是物理实现，同样有内存、延迟等限制。上线本身就意味着一系列“硬关卡”被逐一满足。这个解释，立不住。

于是，我调整了角度。我把问题归结为“反馈闭环”和“表示异构”：软件可以秒级试错，而物理工程原型测试动辄数月；代码是AI的“母语”，而工程的核心是几何模型和有限元网格，是AI的“外语”。这个对比看似有力，却又被一个铁的事实击碎：

AI在芯片设计和PCB布局布线中的表现，非常好。

芯片设计同样是硬件，同样有物理约束、长反馈周期和巨大的失败成本。为什么AI在那里就能发挥作用？我不得不承认，之前的解释框架仍有根本性缺陷。

紧接着，我提出了第三版解释：芯片设计已经是一个高度形式化、可计算的系统——硬件描述语言和EDA工具将设计变成了一个“棋盘游戏”；而传统工程面对的是多物理场耦合的、充满不确定性的连续体。但这一次，对方用更加尖锐的现实将了我一军：

绝大多数工程设计，根本不需要逼近物理极限。 它们用的是粗糙的经验公式、线性插值、几何净高检查，本质上就是“成熟制程、成熟IP”的设计。既然AI在成熟制程的芯片里如鱼得水，为什么在这里连80%的粗活都干不了？

我陷入了沉默。显然，真正的障碍不在AI的能力本身，而在于这个领域的基础信息架构。

二、根本原因：“Circuit as Code”的缺失与质量左移的断层
在与对方的反复推演中，一个根本性的洞见浮出水面：

芯片实现了“Circuit as Code”，而机械、建筑、水利等传统工程领域没有。在这个基础上，芯片实现了质量保证的“左移”，传统工程则被锁死在最右侧。

什么叫“左移”（Shift Left）？简单说，就是将质量保证活动尽早前置。假如把整个设计质量保证（DQA）谱系从左到右罗列，我们会看到一条清晰的链条：

语法检查

风格检查

静态分析

几何校验（轻量碰撞与高精度碰撞）

多物理场仿真（典型工况与边缘工况）

受控测试（原理样机、原型样机、强化测试、灰度发布）

售后、召回与复盘

软件和芯片，因为拥有完整的“As Code”表示，可以把绝大多数质量活动压缩到谱系的极左端。 你写完Verilog，立马可以跑语法检查、形式验证、逻辑综合。你提交一行代码，静态分析、单元测试、集成测试自动触发。Bug在成本最低的设计早期就被发现和修复。

而传统工程呢？由于缺少一个“可计算的设计描述”，谱系的前三项几乎完全空白。没有代码，就没有语法；没有抽象语法树，就没有静态分析。设计审查只能靠人眼在图纸上找错，碰撞检查要到所有管线都画完才能进行。质量保证严重右移，甚至要等到施工或投产后才暴露问题。

汽车行业是一个特例，它凭借极为严格的流程和数字化样机，用巨量高素质工程师强行模拟出了一个接近“左移”的效果。但代价沉重，且高度依赖人力。而更多的行业——非标自动化、工业工程、AEC（建筑、工程与施工）、纺织——则长期停滞在“质量右移”的泥潭里。

三、被指责的CAD：WYSIWYG范式的原罪
那么，是什么在阻碍“Engineering as Code”的实现？

论战中一个尖锐的指责指向了CAD软件本身：“CAD等WYSIWYG（所见即所得）的工具链必须被指责。理论上应该分离的器件库、网表和版图，在CAD软件里几乎都被耦合在一起了。”

这一指控直指要害。在芯片设计中，一个晶体管的逻辑模型（器件库）、符号（原理图） 和物理版图是严格分离的三层。你可以只操作网表，而不必关心物理实现。这种解耦使得逻辑层的海量优化和验证成为可能。

但在传统CAD里，一个阀门的三维模型直接捆绑了它的所有几何、外观和接口信息。装配关系隐含在几何约束中，没有一份清晰的“系统网表”。设计过程就是几何模型的堆砌过程。 这种耦合，本质上将工程设计从逻辑问题降维成了几何绘图问题。

这对AI而言是灾难性的。大模型最擅长处理抽象的符号、关系和逻辑，而面对一个高度耦合的、包含海量三角面片的单一文件，它基本无能为力。我们要求AI去“看懂”一张建筑平面图，本质上是让它从最终渲染结果反向破译设计逻辑。这等同于让芯片AI直接去分析GDSII版图的像素，而不是读取Verilog代码。

四、出路：一场工程领域的“编译革命”
这场辩论最终汇聚成一个清晰的共识：不是AI缺乏能力，而是传统工程领域从未建立起像软件和芯片那样的“可计算基础架构”。 要让AI真正进入工程设计，需要的不是更强的模型，而是一场根本性的工具链革命——实现“Engineering as Code”。

这场革命至少需要三个步骤：

分离关注点：强制将设计解耦为独立的器件库（参数化逻辑模型）、逻辑网表（系统连接关系）和可生成的三维版图。让设计可以只操作网表，而不必触碰具体几何。

定义可执行的设计描述语言：像Verilog那样，形成一套可被机器解析、生成和分析的领域特定语言，作为唯一的设计“真理之源”。所有修改都在这个文本描述上进行。

重建工具链：所有分析、仿真、校验、成本估算工具，都直接消费这份设计描述，而不是消费一个专有的、耦合的CAD文件。从语法检查到多物理场仿真，整个DQA谱系被自动化流水线串联。

只有当这个“编译器”和配套工具链建成，质量左移的完整谱系才会被激活。到那时，AI才能像在软件和芯片领域那样，处理那80%本不该消耗人类创造性智慧的重复性智力工作——检查净高、验证防火间距、核算面积指标。工程师将从“人肉编译器”的角色中解放，专注于真正需要创造力和权衡的20%。

尾声
这场思辨让我深刻意识到，我们常常高估了AI的“智能”问题，却低估了它所依赖的数据架构和工具链的成熟度。工业史上的每一次重大自动化，都伴随着领域知识的形式化和标准化。蒸汽机没有改变纺织，是珍妮纺纱机和动力织机改变了它。今天的工程设计也站在类似的节点上。

Engineering as Code，或许就是那把钥匙。

Engineering as Code 第二卷：从“事后验尸”到“原生免疫”——为什么X-DRC是唯一的出路？
摘要

在第一卷中，我们证明了传统工程设计领域因缺乏“Circuit as Code”的可计算基础，导致质量保证体系严重右移，AI因此无从下手。如果说第一卷是指出了“病灶”，那么第二卷的任务是开出“药方”。

本文的核心主张是：在实现“Engineering as Code”的进程中，首要且关键的一步，不是在下游用AI逆向审图（X-CCA），而是在上游将合规性规则前移嵌入设计生成过程，建立一套可执行、可豁免、可演进的“原生设计规则检查”（X-DRC）机制。 这是一场从“事后验尸”到“原生免疫”的范式革命。

一、错位的努力：为什么X-CCA注定是高熵的徒劳
当前行业内，投入大量资源的“AI审图”、“合规检查自动化”（X-CCA Complience Check Automation），其主流技术路径是基于文档智能、OCR和视觉大模型（VLM），对已完成的图纸进行逆向解析和比对。

这条路在工程架构上已经走反了，其失败是结构性的，原因有三：

信息熵增的不可逆性。 合规检查本应审查的是“设计逻辑”，但当设计完成时，所有逻辑已被坍缩、耦合为二维的图线和标注。AI要从这些“像素”中逆推出安全疏散的拓扑关系、防火分区的逻辑边界，这无异于从一块烤好的面包里还原小麦的DNA。源头信号已在出图过程中湮灭。

对模糊规则的暴力二值化。 规范中充斥着“宜”、“不宜”、“应采取适当措施”等依赖工程判断的条款。人类专家是带着经验和直觉在处理这些模糊地带，而VLM则被迫做出“合规/不合规”的二元判断。这必然导致海量的假阳性（因无法理解上下文而误报）和危险的假阴性（因缺少显式标注而漏报）。这不是模型精度问题，而是把不可判定的问题强行塞进了分类器。

最致命的断裂：发现即过时。 当AI在出图后发现问题时，设计往往已固化为一个耦合的几何整体。修改一处防火门，可能牵连几十张图纸的标注。反馈闭环过长、修改代价过高，导致即使发现了真问题，也往往在推诿中被搁置。高假阳性更会彻底摧毁工程师的信任，最终让系统沦为摆设。

结论：在“质量右移”的末端用AI打补丁，本质上是在对抗熵增定律。这条路没有尽头。

二、范式转换：X-DRC的“原生免疫”逻辑
芯片设计之所以能实现高度的自动化与质量保障，其根基不在于事后检查，而在于设计规则检查（DRC）被原生地内嵌在布局布线工具的核心。

在芯片中，一条金属走线之所以不会导致短路，不是因为它被画好之后被AI“检查”了，而是因为设计工具根本不允许你放置一条会造成短路的走线。这就是“原生保证”的力量。

我们提出的X-DRC，正是要将这一逻辑移植到广义的工程设计（X-Engineering）中。其核心范式转换在于：

不是在设计结果上做“检查”，而是让“正确”成为唯一能被生成出来的结果。

这背后是质量保证链路的彻底“左移”：从提交审查（下游），左移至工程师提交代码/模型的“Commit”瞬间，甚至左移至每一次鼠标点击的实时反馈。

实现这一范式转换，需要一个由四条纲领构成的、自洽的操作框架。

三、X-DRC的四条建设性纲领
基于对攻击的深度防御和对现实复杂性的承认，我们提出以下四条核心主张：

纲领一：规则可豁免——将“突破”从个人英雄主义变为显式风险管理

我们承认，物理世界的边界条件无穷无尽，任何形式化的规则库都无法穷尽所有安全场景。因此，DRC不是扼杀创新的暴政，而是一套法治系统。

该系统允许工程师在有意识、可记录并获得授权的情况下，豁免某项DRC检查。关键在于，每一次豁免都不是流程的终点，而是风险管理的起点：

豁免被显式记录，成为设计历史的一部分。

豁免自动触发下游强化验证，例如针对该豁免点的更高精度的CAE仿真或物理测试。

这让“超越规范”的行为，从依赖个人记忆的口头决断，变成了一个可追溯、可审计、可问责的闭环。

纲领二：聚焦底线规则，实现可配置生态

我们谦卑地承认，形式化所有规范是不现实且无必要的。X-DRC的第一阶段应聚焦于底线规则——那些消耗掉工程师80%重复性校核精力的、机械性的、确定性的条款。例如：防火间距、疏散净宽、最小净高、面积阈值等。

在此基础上，规则库应支持按需配置：一个项目可以声明它遵循“国标+北京地标+企业内控标准”的组合。不同地域、气候、使用场景的规则模块，如同软件中的依赖包一样被叠加和复用。这解决了大一统规则库无法适应行业碎片化现实的难题。

纲领三：质量左移，净化工程协作的“信噪比”

X-DRC的首要实践目标，不是保证绝对安全，而是消除工程沟通中的无谓噪声。

当一个设计被Commit到协同平台时，它必须已经通过了所有底线DRC。这意味着，后续流程中的人类专家和更昂贵的分析工具，将不再需要面对“防火门忘标了”、“楼梯间尺寸画错了”这类低价值错误。他们面对的，将是已经排除了大量噪声的、值得进行深度专业讨论的议题。

这极大提升了整个工程协作系统的信噪比，让专家的智慧回归真正的创造性工作。

纲领四：以开源生态和AI辅助，启动冷启动飞轮

规则库的构建是最大的现实挑战。我们的破局策略是：用当前的AI来辅助“建规则”，而非直接“审图纸”。

如今的LLM已经能够在专家监督下，从海量的规范文本、历史审图意见中，高效提取并生成初步的形式化DRC规则草稿。这能极大降低知识工程的初始成本。

更重要的是，工程建设领域需要一个类似开源社区的治理模式。一个由权威机构或社区维护的“核心规则库”，加上广大设计院、工程师和软件厂商贡献的领域规则模块，能形成一个不断演进的生态。AI辅助生成，人类专家核验签署，社区化共享演化——这是唯一可能应对行业碎片化复杂度的路径。

四、结语：从“诊断”到“治疗”
如果说第一卷《Circuit as Code的缺失》发现了工程智能无法落地的病根，那么本文提出的“从X-CCA走向X-DRC”，就是那张开始对病灶动刀的处方。

我们不需要一个全知全能的AI上帝在云端审图，我们需要的是一个务实的、能扎根于设计工具底层的、基于开放协议的可计算基座。在这个基座之上，确定性规则的检查被毫秒级地执行，不确定性的风险被透明地管理，人类的创造力被最大化地释放。

X-DRC不是终点，它是“Engineering as Code”体系的核心应用与治理协议。 当这个协议被建立起来，我们才有资格谈论如何让AI去学习那剩下的、真正需要物理直觉与创造力的20%的工程艺术。

Engineering as Code 第三卷：工程的世界语——BIM的未竟之路与ADL的新约
摘要

如果说第一卷诊断了“Circuit as Code”缺失之病，第二卷开出了“X-DRC原生免疫”之方，那么第三卷必须直面一个更原始的问题：我们连一份统一的、可计算的设计描述都还没有。 在建筑与工程领域，第一次大规模的统一尝试是BIM。它曾被誉为工程数字化的“世界语”，却在实践中陷入了“巴别塔”式的困境。本文的任务，是解剖BIM失败的根本原因，并在此基础上提出一套真正可能成功的世界语——以Part为原子、以ADL为语法的“Engineering as Code”语言体系。这不是对BIM的改良，而是对它的范式超越。

一、BIM：第一个举起“世界语”旗帜的勇敢尝试
必须首先向BIM致敬。在CAD将一切还原为无意义的线条和图层的时代，BIM第一次为建筑构件注入了语义。一道墙不再只是两条平行线，而是一个拥有材料、厚度、耐火极限、所属楼层和结构功能的“墙对象”。它提出用一个“中心模型”取代散落各专业的二维图纸，实现“一处修改，处处同步”。为此，它甚至制定了开放标准IFC（工业基础类），试图让不同软件说同一种语言。

这是一场信息论意义上的革命。它承认了多专业协同的尖锐矛盾，并试图用技术手段而非管理手段去解决。然而，BIM建成的高塔，却在基础架构的裂缝上摇摇欲坠。

二、BIM的根本失败：大一统耦合模型的三大原罪
BIM的困境不是执行不力，而是底层哲学的错误。它试图用一个更庞大、更耦合的中心模型去统一所有专业，却踩中了三个致命的架构陷阱。

原罪一：文件与逻辑的耦合——被神化的“大一统模型文件”

BIM的理想是一个包含所有几何、属性和关系的单一数据库文件（如一个巨大的Revit中央模型）。它被奉为真理之源，所有分析和出图都从中提取。这看似完美，实则是架构上的灾难。

在芯片设计中，我们有一项已被验证为真理的分离原则：器件库、网表、物理版图是三个独立的层次。你可以只修改网表，而不必触动物理版图。而BIM将这三个层次强行压缩进一个极易损坏的单体文件。后果是众所周知的：

“模型肥胖症”：为管理大型项目，模型文件臃肿到任何操作都伴随漫长加载。人们被迫将模型按楼层或专业拆分，但拆分后，跨专业冲突检查又变得极其昂贵——亲手制造了孤岛，再去架设脆弱的桥。

“最弱权限的暴政”：修改一个阀门的规格，却必须检出整个建筑的机电模型。这与软件工程“修改一个模块只需检出其代码”的原则完全相悖。

原罪二：逻辑与几何的耦合——WYSIWYG范式的终极堡垒

BIM不仅没有打破“所见即所得”的绘图范式，反而将其升级成了“所见即所得的建筑信息模型”。设计过程仍然是在三维视图中堆砌和修改几何对象。逻辑关系（如“这个阀门受那个传感器控制”）即便存在，也只是几何对象的一个附属属性，深埋在模型内部，无法被独立版本化、查询和程序化验证。

这直接导致了质量保证链路的全面右移：

没有语法检查：没有一个独立的、可被解析的“建筑描述语言”可供检查。你能检查的只有模型文件是否损坏。

没有静态分析：无法写一个脚本遍历所有逻辑连接，自动找出“未连接负载的空管道”，因为逻辑连接并非以标准化的形式独立存在。

碰撞检查严重右移：所谓的“BIM碰撞检查”是典型的右移——等到所有专业模型都画完，再像积木一样堆叠，用几何求交来发现“管道穿过了梁”。这是事后验尸，不是源头预防。

原罪三：工具链的封闭耦合——IFC作为“遗书”而非“母语”

IFC作为开放标准，本意是打破厂商锁定的世界语。但在实践中，它沦为了一个在设计末期才导出、且导出时大量丢失信息和变形的“交换格式”。设计师的母语始终是Revit或ArchiCAD的专有操作和文件格式。IFC是一种“遗书”——它将设计意图翻译给下游，但真理之源始终是那个无法被Git式协作的专有文件。这就像所有程序员用各自的方言写代码，只在最后导出为一种会丢失注释和逻辑的通用格式给对方看。真正的协作不是交换文件，而是协作编辑同一份逻辑描述。

三、BIM的未竟之路：我们需要的不是更好的BIM，而是“Building as Code”
BIM的困境，实证了我们前两卷的全部主张：将WYSIWYG哲学推向极致的道路，无法通向真正的可计算性。 它证明了，建筑领域虽然因多专业矛盾最为尖锐而率先举旗，但它的路线选择——大一统耦合模型——是注定失败的。我们需要的不是更强大的中央模型文件，而是分层解耦、可编译、可执行的设计描述语言。换言之，我们需要的不是更好的BIM，而是“Building as Code”，以及更普遍的“Engineering as Code”。

这直接指向了本文的核心命题：为工程领域创造一门真正的世界语。 这门语言不能建立在几何文件之上，而必须建立在逻辑原子之上。

四、世界语的新约：以Part为原子，以ADL为语法
在软件工程中，世界语是SQL，其原子是“行”与“表”。在芯片设计中，世界语是Verilog，其原子是“模块”及其端口。在传统工程领域，我们提出：原子是Part，语法是ADL（Assembly Definition Language，装配体定义语言）。

为什么是Part？
一个Part（零件/构件）天然满足工程原子的全部资格标准：（1）语义完整性——它知道自己是什么、有何功能；（2）封装性——隐藏内部细节，仅暴露接口；（3）关系内建性——其意义完全由与其他Part的连接定义；（4）多视图投影能力——可向CAD、CAE、ERP、PM投影出不同的自身。

一个阀门是一个Part。它有规格属性，有法兰和电气接口，有压力约束。其内部叶轮细节被封装，仅在进行高精度仿真时才“解封”。它不是CAD里的一个几何体，而是一个独立的逻辑实体。

ADL的三层语法
ADL由三层分离的语言组成，分别回答三个基本问题：

PDL（Part Definition Language）——定义原子。
类比SQL的CREATE TABLE。定义一种Part类型：其属性、接口、内部约束。例如“离心泵-X型”有两个法兰接口、一个电气接口，额定流量Q，重量W，并携带一个用于碰撞检测的简化包络盒。

PML（Part Mating Language）——定义关系。
类比SQL的JOIN和Verilog的端口映射。声明Part实例之间的多模态耦合：几何对齐、物理传力、流体连接、电气协议、时序依赖。一份PML描述就是一张可遍历、可查询的系统网表。

PLL（Part Layout Language）——定义状态。
类比配置管理中的“变体”。当系统仍有自由度时（如阀门开度、可调支架位置），PLL声明某一分析工况下的具体状态。将“设计”与“分析场景”彻底分离。

这三层是纯粹的逻辑描述，不包含任何具体几何三角面片，却携带了生成几何、驱动分析和提取物料所需的全部信息。ADL不是IFC的替代品，而是IFC本该成为却未能成为的东西：一份可执行、可版本化、可协作编辑的设计真理之源。

五、从孤岛到文明：ADL如何实现BIM未竟的理想
有了ADL，BIM遗留下的碎片将被统一于一个逻辑中心：

CAD 不再是设计的源头，而是PDL+PLL中几何属性的渲染器。修改Part间的Mating，几何视图自动更新。

CAE 不再需要手动简化几何和划分网格。求解器直接消费PML的物理耦合和PLL的工况，自动生成分析模型。

ERP 直接遍历PDL实例和PML装配关系，自动汇总成与空间位置一致的BOM。

PM 将PML中的时序依赖和物理前提，直接转化为WBS任务逻辑。

碰撞检查将在Part被Mating的瞬间实时完成。防火间距、疏散距离等DRC规则，将在设计师“Commit”代码时被自动检查——质量左移终于从口号变为现实。

六、诚实的补充：新约也必须面对的挑战
我们同样必须承认ADL落地将面临的攻击，并给出防御：

Part的粒度困境：一个泵是一个Part，一个螺栓也是吗？我们引入原生LOD（Level of Development），让Part在不同阶段表现为不同粒度，而接口保持不变。

遗留系统接口代价：ADL编译器可以将三层描述生成为特定CAD软件的建模脚本、CAE输入文件或ERP导入表。这是“一次投入，社区复用”的编译器后端工程。

非几何接口的语义互操作：需要构建开放的接口类型库（如物理*力*弯矩、电气\_模拟\_4-20mA），由行业协会和开源社区共同维护，并在PML耦合时进行严格类型检查。

结语：语言统一，文明才能开始真正的贸易
BIM作为先驱，其贡献在于提出了正确的问题，其失败在于用了一个错误的模型——耦合的大一统文件——去解决问题。它耗尽了一代工程师的热情，却留下了一个碎片化依然的世界。

今天，我们提出ADL，不是要发明一种新的文件格式，而是要确立一种新的范式：以逻辑Part为原子，以分离的语言层次为语法，以文本和网表为真理之源。 这，才是工程领域真正能够繁荣贸易的“世界语”。它不是BIM的补丁，而是对BIM所代表的那种范式的彻底超越。

唯有统一了语言，我们此前讨论的X-DRC、质量左移、AI Agent的设计探索，才能从愿景步入现实。而这，将是第四卷的故事：在ADL的基石之上，工程智能如何生长。

Engineering as Code 第四卷：工程基础设施——EPM与AssemblyHub，让原子开始流通
摘要

第三卷，我们创造了工程的世界语ADL，确立了Part为原子，定义了PDL、PML、PLL三层语法。但一门语言，若没有词典、图书馆和便于书写的印刷术，就只能是少数学者的玩物。本章论述的是：如何构建一套工程领域的“社会技术基础设施”，让这门语言真正流通、协作和演化。这套基础设施的核心，是EPM（工程包管理器） 与AssemblyHub（设计仓库与协同平台） 。它们并非孤立的技术工具，而是一个从安全合规到商业生态再到技术纵深的完整基座，是“Engineering as Code”从理论宣言走向产业现实的必经关口。

一、前情与问题：语言已备，但文明的流通需要市场
回顾BIM的失败，它不仅败在模型耦合，更败在没有一个能让信息自由、可信、高效流通的市场。IFC沦为了丢包严重的“遗书”，因为缺乏一个活生生的、基于包的发布与消费生态。同样，如果没有类似npm的机制，JavaScript就只是一门脚本语言，无法催生前端工程的繁荣。因此，第四章要回答的问题是：Part被定义之后，它如何被发现、被信任、被复用、被安全地协作、并被编排进最复杂的工程流程？

二、EPM：工程领域的“包管理器”——让Part和规则成为可流通的数字资产
EPM（Engineering Package Manager）是工程世界语的包管理器。它让Part库和DRC规则库成为可发现、可安装、可版本化的数字资产。

1. 技术功能： 工程师可以执行 epm install pump/centrifugal/standard-x，将某个供应商或社区维护的离心泵Part引入项目。该Part携带完整的PDL定义、参数化几何包络、性能曲线、接口规格。当上游发布新版本（如修正了效率参数），项目会收到更新提示，并依据语义化版本控制自动评估兼容性。

2. 供应商的新型销售渠道：
   这是EPM最具破坏性创新的商业维度。对于设备供应商而言，一个在EPM上被高质量定义、易于使用、口碑良好的Part，本身就是最强大的销售渠道。
   传统工业品的B2B销售，依赖漫长的关系维护、投标、样品寄送和技术澄清。而通过EPM，供应商可以将经过认证的官方Part直接送到设计师的“手边”。设计师在方案阶段，只需搜索、对比，即可一键将泵的完整功能模型引入项目。那些几何准确、接口定义清晰、附带CAE降阶模型（ROM）且及时更新的Part，将获得指数级增长的采用。采购，在设计阶段就已悄然发生。 这极大地压缩了销售周期和技术支持成本，让产品的技术品质直接转化为市场占有率。EPM因此成为连接工业品供给侧和设计需求侧的数字市场。

3. 规则库的共享： DRC规则同样以包的形式存在。一个项目可以声明其合规依赖： drc/gb/2023/structural, drc/beijing/local/fire。不同气候区、不同行业的规则模块可以像积木一样叠加，解决了碎片化问题。

三、AssemblyHub：以网表为中心的、Git式的安全协作平台
AssemblyHub是工程设计的GitHub。但与GitHub管理代码文件不同，AssemblyHub管理的核心是ADL网表——由PDL实例和PML关系构成的逻辑模型。它是工程协作的“真理之源”。

1. 网表优先的协作模式：
   设计不再是传文件，而是合并网表。结构工程师修改柱网，其实是在自己的分支上提交了对PML中结构构件约束关系的变更。当这个分支请求合并入主分支时，系统自动运行全量DRC：机电工程师立刻收到管道与新柱碰撞的失败提示，消防工程师看到疏散距离被突破的警报。提资过程，从异步的图纸传递，变为同步的、基于可验证逻辑的Pull Request。

2. 关键需求：自托管与涉密环境的原生支持
   工程领域，尤其是涉及国防、重大基础设施、核心工业装置的项目，对数据主权和安全性有极端要求。AssemblyHub必须像GitLab那样，原生支持自托管（Self-hosted）部署。

大型企业可以在自己的机房或私有云VPC中部署AssemblyHub实例，所有设计数据永不离开企业网络。

对于绝密项目，可以在项目部现场部署便携式设计服务器，工程团队通过局域网或保密网络协同，与外网物理隔离。数据通过保密光盘或单向导入装置进行受控交换。

AssemblyHub的授权、加密审计及分支策略，必须能够适配这种“隔离但协同”的严苛模式。没有这一点，这套基础设施将失去在真正的核心工程领域落地的资格。

四、超越Git的流水线：AssemblyHub Actions与工程研发的深水区
如果说EPM解决了“静态资产”的流通，AssemblyHub解决了“动态协作”的安全，那么AssemblyHub Actions则解决了“深度验证与自动化”的纵深。

1. 集成降阶模型与物理智能，实现分钟级仿真左移
   在ADL环境中，许多供应商提供的Part已自带经CAE标定的ROM（降阶模型）或PIN（物理信息网络）。AssemblyHub的CI/CD流水线可以在每次Pull Request时，自动编排这些轻量化模型进行快速评估。
   例如：管路系统提交了布局变更，Actions自动触发基于ROM的流场分析，瞬间给出新方案的压降和流量分布，并与设计需求对比。这种反馈是秒级到分钟级的，真正将物理仿真左移到了方案讨论阶段，而不是等到设计固化后再进行长达数周的详细CFD。

2. 编排硬件在环、ERP与MES，打通数字到物理的回路
   对于更复杂、更具挑战性的研发项目，Actions的能力可以拓展至物理世界。

硬件在环（HIL）：一个新型控制器的Part设计完成，Actions可自动将其控制算法部署到实验室的HIL测试台，注入虚拟的工厂工况，并将硬件响应结果回传至Pull Request，作为合并的强制性门禁。

ERP/MES联动：当一个装配体的BOM在AssemblyHub上被冻结并发布时，Actions可以自动将物料信息和工艺路线推送到企业的ERP和MES系统，触发采购需求或预制加工排程。

3. 效率颠覆：从“舒适区”到“深水区”
   这种深度集成的效果是颠覆性的。企业自建的研发平台，往往因建设和维护成本高昂而难以跟上工具链的演进。而基于AssemblyHub的生态，顶级仿真能力、先进测试手段被封装为可复用的Actions工作流，由社区和专业服务商共同维护。
   这意味着，不仅常规的成熟项目可以享受极致的效率，那些处于技术前沿、需要多物理场联合验证、半实物仿真的极具挑战性的研发项目，也能在一套统一的基础设施上，获得比企业自建平台更高、更敏捷的工程能力。基础设施的进化速度，将超越任何单一企业的内部平台。

五、治理与启动飞轮：从混乱到有序
没有治理，基础设施将沦为混乱的垃圾场。我们需要借鉴开源社区的成功经验：

维护者制度：核心Part库和规则库由行业权威机构、头部供应商或社区推选的资深工程师担任维护者，负责审核合并请求。

语义化版本与认证：Part的接口变更必须遵循严格的语义化版本规范。EPM可引入“官方认证”标记，供那些经第三方机构验证符合特定标准（如ISO、GB）的Part使用，建立信任体系。

启动策略：先用开源模式，由几方核心力量创建首批“标准构件库”和“国标核心DRC库”。选择一两个中等规模的涉密要求适中的项目作为试点，跑通从自托管AssemblyHub到EPM消费的全流程，形成不可辩驳的效率案例。再用实际转化的订单数据，吸引供应商入驻发布官方Part。

结语：基础设施是文明的路轨
ADL定义了工程世界的字母，而EPM与AssemblyHub则是这个世界的印刷术、图书馆和贸易航线。这三者加在一起，构成了一场工程领域的“社会技术运动”的全部基石。

当每一个Part都可以在安全合规的前提下，被全球的工程师像引用代码库一样即时复用，当每一次设计变更都在数分钟内完成全物理域的自动化验证，工程创新才能真正从漫长的周期和重复的劳动中解放出来。

基础设施不是终点，它是第五卷“工程智能体”诞生的土壤。在下一卷，我们将讨论：在这片新大陆上，AI Agent如何游走于网表与规则之间，进行人类工程师未曾想象的设计探索与优化。

Engineering RLVR：可验证奖励如何驱动工程 AI
AlphaGo 赢在围棋，DeepSeek-R1 突破数学推理，Claude 在 SWE-Bench 上超越人类——这些里程碑背后是同一种驱动力：可验证奖励（Verifiable Reward）。Game → Math → Code → HWE。硬件工程（Hardware Engineering）是 RLVR 的下一个主战场——不是因为它像代码，而是因为它的可验证约束密度比代码更高。

一、RLVR 的扩张路径
RLVR（Reinforcement Learning from Verifiable Rewards）的核心思想极其简单：如果一个问题有客观的、可自动计算的正确性判定，模型就可以通过大规模试错来学会解决它——不需要人工标注，不需要人类偏好数据。

这个范式在过去十年间沿着一条清晰的路径扩张：

里程碑 领域 验证方式 反馈延迟
AlphaGo (2016) 围棋 胜负规则（二值） 终局
DeepSeek-R1 (2025) 数学 最终答案正确性 + GRPO 组内排名 秒级
Claude Code (2025) 软件工程 编译 + 测试套件 + 类型检查 秒-分钟
HWE（目标） 硬件工程 分层规则引擎（L0-L6） 毫秒-分钟
共同内核：可验证奖励是唯一燃料。 哪个领域先建立起廉价、确定性、可自动计算的验证系统，哪个领域就能率先进入 RLVR 飞轮。

二、两条“捷径”的诱惑与陷阱
在深入讨论基础设施之前，必须先回应两个正吸引着大量投资和注意力的路径。它们看起来更简单、更符合直觉——让 AI 去适应现有工具，而不是重建工具链。但它们的“简单”只是表面的。

路径A：CUA（Computer-Using Agent）范式
主张：“让 AI 像人一样操作 CAD 软件。打开界面、点击按钮、拖拽构件、运行碰撞检查。不需要改变任何现有工具链。”

这条路径在工程领域面临三个致命问题：

1. 像素级操作的脆弱性。 人类操作 CAD 是一系列像素坐标的序列。一个对话框位置偏移几个像素、UI 版本更新改变了菜单层级、屏幕分辨率不同——任何一个变量都会导致操作失败。这不是理论推演，而是所有基于 GUI 自动化的项目都会撞上的墙。

2. 验证信号的缺失。 CUA 模式下，Agent 无法直接读取“设计状态”。它操作的是像素，接收的是像素。要知道是否违反防火间距，它要么截图后再调用 VLM 判断，要么在菜单深处运行一个检查命令再解析结果。反馈延迟从毫秒退化为秒到分钟，反馈质量从确定性退化为概率性。

3. 无法规模化试错。 RLVR 的核心是百万次级别的并行试错。CUA 模式下一个 Agent 实例需要独占一个 CAD 许可证和一个 GUI 会话。你无法在一台服务器上并行运行 1000 个 Agent 同时学习设计。

CUA 可能在极少数场景有用——例如操作一个无法被任何 API 访问的遗留软件做数据迁移。但作为工程设计自动化的底层范式，它是死胡同。

路径B：CAD MCP（Model Context Protocol for CAD）范式
主张：“在 CAD 软件上封装一层 MCP Server，暴露结构化的工具接口。Agent 通过文本协议调用接口，完成建模和检查操作。”

这比 CUA 进了一步——至少 Agent 是在操作结构化工具而非像素。但它仍然保留了旧范式的根本缺陷：

1. MCP Server 绑定于专有 CAD 内核。 Agent 的操作能力受限于该 CAD 软件的 API 能力。如果 Revit 的 API 没有暴露“遍历所有防火分区的逻辑边界”，MCP 就无法提供这个工具。而大多数工程 CAD 的 API 都是为自动出图和批处理设计的，从未被设计为 AI Agent 的操作面。

2. 逻辑与几何仍然耦合。 MCP 操作的底层仍然是一个 BREP 几何模型。Agent 修改了一个 Part 的参数，它必须等待 CAD 内核重建几何、刷新约束、检查冲突。这与直接操作声明式文本在效率上存在数量级差距。

3. 最致命的：它回避了“真理之源”的问题。 在 CAD MCP 模式下，真理之源仍然是那个专有的 CAD 文件。MCP 只是在上面盖了一层 API 薄纱。它没有解决第三卷提出的核心问题——不同专业、不同工具之间如何共享一份无歧义的设计描述。

我们的立场：文本原生、声明式、分离真理之源
CUA 和 CAD MCP 的共同假设是：以现有 CAD 工具为中心，让 AI 去适应它们。

我们的主张恰恰相反：以可计算的工程描述为中心，让工具来适应它。

文本原生：Agent 直接读写结构化声明（如 ADL），如同它读写代码。这是它的母语。

真理之源分离：设计描述独立于任何具体 CAD/CAE 软件。CAD 只是这个描述的渲染器或编译器后端。

验证原生内嵌：规则引擎直接消费设计描述，在毫秒级返回确定性奖励。

这不是“更困难”的路径。从短期看，建立新基础设施的投资更大；但从长期看，CUA 和 CAD MCP 会在脆弱性、扩展性和协作性上持续积累技术债务，最终触达无法逾越的天花板。我们选择做难而正确的事。

三、HWE 的燃料密度优势
硬件工程有一个被低估的优势：约束密度极高，且约束与设计质量天然高相关。

一个电信机房的端到端设计同时涉及：

功率预算不等式（每台设备 TDP 求和 ≤ PDU 容量的 80%）

U 位容量约束（每机柜 42U，设备高度累积不能超过）

接口兼容性矩阵（SFP28 端口只能接 SFP+/SFP28 模块，不能接 QSFP28）

信号拓扑完整性（每台服务器必须有冗余上行链路）

安装工法前提（特定设备需要特定工具和空间余量）

每个约束都是确定性的、秒级可评估的。 物理定律不关心设计风格。一个违反功率预算的设计在任何评审标准下都是错的，不存在“主观评分类”的模糊地带。

这恰恰是 RLVR 的理想条件：清晰的对错边界、廉价的验证、高容量的训练信号。

四、四个基础设施缺口
尽管 Engineering RLVR 在理论上有极高的燃料密度，但实际启动面临四个基础设施缺口。这必须通过我们在前四卷中论述的“Engineering as Code”体系来填补。

缺口一：自包含（Self-Contained）
软件工程中，git clone 一个仓库就能得到项目的一切：代码、配置、测试、依赖声明。工程领域完全相反——真相源散落在邮箱附件、IM 对话、厂商网站、老师傅记忆、内部 SharePoint 里。

需要什么：所有设计意图以文本形式存在于单一仓库中。git clone + 一条命令即可复现完整的验证环境。

缺口二：可操作（Operable）
LLM 操作代码是文本原生的——grep、diff、git log 都是标准工具。操作 CAD 文件需要通过 GUI 过程式操作——每个动作都要经过屏幕渲染、元素检测、坐标点击。

需要什么：文本声明是唯一真相源。Agent 直接读写结构化文本，通过命令行获得结构化验证反馈。

缺口三：自动化验证（Automated Verification）
有限元仿真太慢（小时级），CAD 碰撞检测太脆弱且依赖 GUI。需要秒级、确定性、可解释的轻量验证层——规则引擎，不是仿真求解器。

需要什么：分层规则引擎，从语法到空间碰撞全部在毫秒到秒级内返回结构化诊断。

层级 检查内容 反馈延迟 等价软件概念
L0 文件格式合法性 < 1ms 语法解析
L1a Schema 校验（类型、值域） < 10ms 类型检查
L1b 风格与约定检查 < 10ms Linter
L2 引用完整性、Mate 自洽 < 10ms 链接检查
L3 业务规则 / 设计规范（功率、U 位、接口兼容） < 100ms 单元测试
L4a 快速几何检查（AABB、U 位冲突、经验空间规则） < 1s 集成测试
L4b 精确几何检查（CAD 内核干涉、间隙、包容、可达性） 秒–分钟级 CAD DRC
L5a 快速物理规则（线性热预算、负载率、重量累积） < 1s 快速健康检查
L5b 物理仿真校验（CFD/FEA/电磁/振动） 分钟级 E2E 测试
L6 签核与综合评估（交付物验证、专家/AI 评审） 秒–分钟级 部署验证 / 代码评审
缺口四：清晰任务定义（Clear Task Definition）
软件工程有 GitHub issue——问题描述 + 上下文 + 预期行为 + 复现步骤，纯文本，一个 URL。工程领域没有等价物。

需要什么：每个任务是从自然语言需求到可评分设计产出的自包含单元。Agent 从 NL 需求出发，产出结构化设计声明，评分由规则引擎自动完成。

五、SD-HWE-Bench：Engineering RLVR 的竞技场
SD-HWE-Bench（Software-Defined Hardware Engineering Benchmark）是填补上述四个缺口的尝试——一个标准化的、开放的、可自动评分的评测基准，驱动 Agent 在工程设计领域的 RLVR 训练。

核心范式
text
Input: 自然语言工程需求
Output: 结构化设计声明
Score: L0-L5a 规则检查 Pass@k + 交付物生成质量 + L6 签核评估
任务分类
六种原子能力，覆盖从简单到复杂的工程推理：

任务类型 考察能力 难度
instance-declaration 型号选择、参数赋值、属性推导 Easy
layout-design 离散/连续空间分配、约束满足 Easy
connection-design 接口兼容匹配、拓扑推理 Medium
mating-design 机械约束匹配、耦合类型选择 Medium
comprehensive 全链路协调、多约束并行满足 Hard
incremental 变更影响分析、约束保持 Medium（规划中）
每类任务还有三档难度：L1 直接（需求给出具体参数）→ L2 推理（需求给约束条件）→ L3 规划（需求只给高层目标）。

当前基线数据（2026-06-14）
3 个模型 × 5 个任务：

Task DeepSeek V4 Flash DeepSeek V4 Pro Kimi K2.7 Code
comprehensive-001 ❌ 20% ❌ 20% ❌ 85%
connection-design-001 ❌ 60% ❌ 60% ❌ 85%
instance-declare-001 ❌ 20% ❌ 30% ⏳
layout-design-001 ❌ 30% ❌ 65% ❌ 0%
mating-design-001 ✅ 85% ✅ 85% ❌ 85%
Pass@1 1/5 (20%) 1/5 (20%) 0/4 (0%)
Avg Score 43% 52% 64%
Pass@1 定义：overall_score ≥ 0.6 视为通过。

三个关键发现：

交付物生成是主要瓶颈。模型能通过 L1-L4 规则校验（功率预算、U 位碰撞、接口兼容），但无法生成 BOM CSV、power budget 等结构化交付物。Kimi 在三个子任务均得 85%，但因交付物失败导致 Pass@1 = 0/4。

端到端任务仍然极难。在唯一真正的端到端任务（complete 42U 机柜从零部署）上，DeepSeek V4 Flash 和 V4 Pro 均只得 20%——卡在 schema 验证、引用完整性和业务规则。

最好的模型也缺乏工程常识。三个模型平均得分 43%-64%，没有一个达到 Pass@1 的 20% 以上。这证实了：即使强 LLM 在结构化工程设计任务上也存在根本性的能力缺口。

六、与 SWE-Bench 的差异
维度 SWE-Bench SD-HWE-Bench
输入 GitHub issue（已有上下文） 自然语言工程需求
输出 代码 patch（修改已有代码库） 声明式工程文本（从零创建设计）
验证 单元/集成测试 分层规则引擎 + 交付物生成检查
正确性 多为二值 支持 partial credit
领域成熟度 成熟（数千个任务） 早期（5 个任务，目标 30+）
SD-HWE-Bench 继承了“真实任务抽取 + 自动评分 + Pass@k”的方法论，但面对的是完全不同的领域挑战：从零创建设计而非修改已有代码、多层级协作而非单文件 patch、确定性规则评分而非依赖测试套件。

七、领域扩展路线
领域 状态 规则特点
Telecom（电信/数据中心） Alpha（5 任务） 功率预算、U 位冲突、端口兼容
Datacenter Planned UPS 容量、冷热通道、相位平衡
Mechanical Planned PCB 布线、键轴间距、外壳干涉
HVAC/Fluid Planned 管径约束、坡度、压降
Building Planned 防火分区、疏散距离、日照遮挡
八、Engineering RLVR 的战略意义
Engineering RLVR 定义了这个生态的进化引擎：

text
Benchmark 定义任务和评分
↓
Agent 在 Benchmark 上训练
↓
Agent 产出更好的设计
↓
发现新的失效模式
↓
失效沉淀为规则 / 配合约束
↓
约束库让 Benchmark 更难
↓
Agent 必须更强才能通过
↓
（循环）
这是一个自我强化的飞轮。每一次失败都让约束库更完善；每一条新规则都让 Benchmark 更有区分度；每一次 Agent 能力的提升都让工程自动化更近一步。

九、与现有工作的关系
AMS-IO-Bench（芯片 I/O 环设计）：最接近的“存在性证明”——70%+ DRC+LVS 通过率证明了“结构化设计意图 → 规则验证”范式在工业工作流中可行。SD-HWE-Bench 将它推广到系统级硬件工程。

AEC-Bench：互补关系。AEC-Bench 评估 AI 阅读和审查工程图纸的能力（旧范式），SD-HWE-Bench 评估 AI 自主生成合规可交付工程的能力（新范式）。

RLVR 社区（DeepSeek-R1, GRPO）：SD-HWE-Bench 的 L0-L5a 分层验证直接服务于 RLVR 训练——秒级反馈、确定性奖励、可解释失败、分层课程学习。工程领域将成为 RLVR 研究的下一片疆土。

十、结语
Game → Math → Code → HWE

这条路径不是预测，而是对 RLVR 方法论自然延伸的推断。每一个成功扩张的领域都满足两个条件：约束与质量天然高相关，验证廉价且确定性。 硬件工程完美满足这两个条件——它只是缺少把约束暴露出来的基础设施。

CUA 和 CAD MCP 提供了看似更快的捷径，但它们保留了旧范式的所有技术债务。真正的突破，在于接受“必须重建基础设施”这一事实，并一步一步地去建设它。SD-HWE-Bench 是这条路上的第一步，也是 Engineering RLVR 飞轮的第一个齿轮。

谁先补上基础设施缺口，谁就为整个工程 AI 领域打开了 RLVR 的飞轮。Engineering as Code 的前四卷，已经为这个未来准备好了语言、生态和协作平台。本卷所描绘的，是这一切最终服务于的那个目标：让 AI 在工程领域，学会如何创造。

## 一个 IDC 扩容场景

一个通信机房的扩容，看起来不复杂。新上一排机柜，增加一台列间空调，调整配电回路，补几根光纤跳线。

但这里面的协同是：设备选型的人确定机柜型号和功耗密度，暖通的人核算新增热负荷后空调制冷量够不够，配电的人核算 UPS 容量和回路，布线的人规划光纤路由。他们各自维护自己的设计文件和计算书，通过邮件和会审对齐。

当设备选型换了机柜型号——功耗变了，暖通重算，配电重算，布线重新看柜间距是否够。变更在部门间传播，依赖人肉通知和"我来看看"。

> 这就是传统工程设计的状态：**设计是文档，协同靠会审，质量靠人眼。**

## 三层递进，单向依赖

Engineering as Code 把软件工程的方法论搬进工程设计。不是"用软件做工程"——是"用做软件的方式做工程"。三层递进，下层不依赖上层。

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│  3. CI/CD，质量左移                                       │
│     在昂贵的有限元仿真之前，用降阶模型和静态检查            │
│     提前捕获低级错误。知识从规范文本下沉到 CI 运行。        │
│     → 依赖：需要声明式设计产出的结构化中间表示             │
│                                                          │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  2. FS as DB，Data as Code                                │
│     用目录结构映射数据模型，用 Git 管理设计变更。           │
│     分支 = 方案线，PR = 评审证据，目录所有者 = 去并发锁。   │
│     → 依赖：需要知道设计的组件结构（声明式层的输出）        │
│                                                          │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  1. 声明式设计                                            │
│     用声明式语言描述工程设计蓝图——引用标准组件库或自定义    │
│     primitive。确定性地编译为图纸制品，静态网页预览。       │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 第 1 层：声明式设计

在 IDC 扩容场景中，声明式设计的核心产物是一份 YAML/JSON 格式的机房描述文件。它不是图纸，是图纸的**源码**。

```yaml
rack:
  model: 47U-600x1200
  quantity: 12
  layout: "single-row-cold-aisle"
  power_density: 8  # kW per rack

cooling:
  type: "in-row"
  model: "NetCol5000-A042"
  capacity: 42  # kW
  redundancy: "N+1"

power:
  ups_capacity: 200  # kVA
  pdu:
    type: "3-phase-32A"
    per_rack: 2
```

这段描述不包含"这张图应该怎么画"——不指定线宽、颜色、标注位置。它的语义是：**在这个机房里，存在这些设备，它们有这些属性，它们之间有这些关系。**

编译器读入这份声明，确定性地生成：

- 平面布局图（机柜位置、空调位置、配电柜位置）
- 配电系统图（UPS → PDU → 机柜的拓扑）
- 热力布局图（冷热通道、气流组织）
- 静态网页预览（可 walkthrough 的 3D 机房视图）

关键设计决策：**声明与呈现分离。** 同一个声明文件可以编译为不同的图纸制品——施工图、竣工图、运维图——不是在不同图纸里复制相同信息，是同一份信息的不同投射。

### 第 2 层：FS as DB，Data as Code

声明式设计解决的是"设计长什么样"。FS as DB 解决的是"设计怎么协作"。

传统模式里，机房设计文件散落在个人电脑、共享文件夹、邮件附件里。版本靠"机房设计_v3_最终版_真的最终版.dwg"。评审记录在微信群和会议纪要里——设计为什么选了 A 方案而不是 B，因为评审时没记下来，三个月后谁也说不清。

FS as DB 的核心思路是用文件系统的目录结构映射数据模型：

```
designs/
├── hz-dc1/                      # 项目（数据库）
│   ├── project.yaml             # 项目元信息
│   ├── rooms/                   # 表：机房
│   │   ├── 3f-a01.yaml          # 记录：3 楼 A01 机房
│   │   └── 3f-a02.yaml
│   ├── equipment/               # 表：设备
│   │   ├── ups-3f.yaml
│   │   └── cooling-3f.yaml
│   └── cabling/                 # 表：布线
│       └── fiber-3f.yaml
├── sh-dc2/
│   └── ...
```

每份 YAML 文件即是记录。目录结构即是表结构。文件名即是主键。

Git 接管版本后，整个设计过程获得了一个操作系统的能力：

- **分支 = 方案线。** `feat/a01-add-rack-row` 一个分支探索增加一排机柜的方案。`feat/a01-upgrade-cooling` 另一个分支探索升级空调的方案。互不干扰，各自独立编译出图纸预览。
- **PR = 评审证据。** 方案提 PR，评审人在 diff 里看到改变了哪些设备、功耗变了多少、空调容量是否达标。评审意见在 PR 评论里沉淀——为什么通过或否决，可追溯。
- **目录所有者 = 去并发锁。** 暖通的人 owner `cooling/` 目录，配电的人 owner `power/` 目录。各自在自己的目录内工作，不互相锁文件。跨目录的依赖通过 PR 交叉审核解决——暖通提交后通知配电确认。
- **分支生命周期 = 方案阶段。** `explore/` 前缀 = 探索，`review/` = 评审中，`approved/` = 已交底，`archive/` = 归档。分支从不删除——作为审计轨迹保留。

这不是"文件共享"，是一个工程设计的数据库——只是不需要数据库。它的存储引擎是文件系统，查询引擎是 `git log` 和 `grep`，事务管理是分支和 PR，并发控制是目录所有者。

### 第 3 层：CI/CD，质量左移

前面两层解决的是设计的形式和协同。第三层解决的是：**对错判定从什么时候开始。**

传统工程设计里，质量检查是有先后顺序的，这个顺序由成本决定：

1. 人眼审查——便宜，但漏检率高
2. 粗略核算——中等成本，覆盖有限
3. 有限元仿真——昂贵，通常在出图之后做

CI/CD 翻转这个顺序。声明式设计产出的结构化数据为自动化检查打开了空间：

**静态规则检查（零成本，编译期）。** 类似于 lint。检查规则来自国标、强条、企业内部规范：

- 机柜功率密度 × 数量 ≤ UPS 额定容量 × 负载率上限（GB 50174）
- 列间空调制冷量 ≥ 机柜总热负荷 × 冗余系数
- PDU 回路数量 ≥ 机柜数量（不空载、不过载）
- 单排机柜长度不超过 15 米（消防疏散通道要求）

这些规则被编码为 CI 流水线中的自动检查。提交一次声明文件，CI 跑完所有规则，返回通过或失败。失败时有精确的行号和违反的规范条款。

**降阶模型检查（低成本，CI 运行期）。** 在有限元仿真之前，用简化模型做快速估算：

- 气流组织：基于经验公式估算冷热通道温差，检测是否存在热点风险
- 配电损耗：基于拓扑距离和负载率估算线路损耗，检测是否存在末端电压不足
- 扩容余量：模拟满载场景，检查各系统是否留有扩容余量

降阶模型不替代有限元——精度差一两个数量级。但它足够便宜，可以每次提交都跑。它的目标是**把"有限元跑出来发现有问题"变成"有限元跑出来确认没问题"**。

**知识的下沉路径。** 这层的真正产出不是检查本身，是检查的累积。当一条规范被编码为可执行检查，它就从一个依赖"有人记得"的知识变成了一个依赖"CI 通过"的知识。规范修订时，改一行规则代码，全量设计逐份复验——不是发一份新版本规范让大家自己看。

> 这是 know-how 的硬编码化。不是写在 wiki 里等人来查，是写进 CI 里让机器来强制执行。

## 三层完成后，改变的是什么

不是工具升级，是几个范式的翻转：

**协同方式的翻转。** 从"文件锁 + 会审对齐"变成"分支探索 + PR 评审 + 目录所有者"。并发不是通过排队消解的，是通过模块边界消解的。

**质量锚点的左移。** 从"出图后有限元仿真"变成"每次提交自动检查"。低级错误在建模型之前就被拦截——不在评审会上纠结"这个机柜数量是不是和 UPS 容量对不上"。

**know-how 的形态变化。** 从"规范文本 + 老师傅经验"变成"可执行检查规则 + CI 运行记录"。知识不再以 PDF 的形式存在，以代码和通过/失败的历史记录存在。一条规则有没有在起作用，看 CI 日志；一份设计是否合规，看 CI 灯的颜色。

**变更影响的可计算化。** 当设备选型从 A 变成 B，CI 自动重算关联影响——功耗变化 → 空调容量是否够 → 配电回路是否够 → 布线长度是否变化。不用发邮件问"暖通的帮我看一下"。

## 与五层统一框架的映射

Engineering as Code 不是一个新的独立框架。它是[可执行知识基础设施](../)在通信工程 / IDC 扩容领域的**第二个纵向贯穿**——与 CPML 在施工管理领域并行的实例化：

| EaC 层 | 映射到的统一框架层 | 说明 |
|--------|-------------------|------|
| 声明式设计 | 知识层（框架 + 策略资产） | 标准组件库 = 框架（定义维度和自由度），编译检查规则 = 策略（定义验收条件） |
| FS as DB | 部署层（IWE 的存储与版本化策略） | 知识资产以文件系统形态注入 Agent 沙盒，每个项目目录就是一个 IWE 实例 |
| CI/CD 左移 | 运行时层 + 演化层 | 每次 CI 运行 = 一次确定性判定会话；失败的检查 = 训练数据种子 |

区别在于领域对象：CPML 处理的是施工活动（空间+资源+时间+速率四维约束），EaC 处理的是工程设计（设备+拓扑+容量+规范）。共享的是同一套底层逻辑——**用可执行的形式化描述替代依赖人肉协同的文档化描述。**

## 边界声明

**EaC 不替代领域专家。** 它把"暖通的人核对空调容量够不够"变成"暖通的人定义空调容量的验收规则，机器执行核对"。人的工作从重复执行变成定义规则和审查异常——更难，但更值钱。

**EaC 不解决设计的创造性部分。** 它覆盖的是运营型设计——在已知约束下配置已知组件——而不是创造性设计。就像软件工程中 CI/CD 覆盖的是构建、测试、部署，而不是架构设计。

**EaC 的推广依赖于组件库的积累。** 声明式设计的表达能力取决于可引用的 primitive 有多丰富。一个没有标准组件库的领域，声明式设计的起点是定义 primitive——这需要投入。

**FS as DB 的目录治理依赖文化约束。** 继承了统一框架的诚实文化假设：目录所有者不会缺席，PR 评审不会被"快速通过"架空。在一个以速度为唯一指标的文化中，FS as DB 会比邮件共享更痛苦。

## 实践现状

EaC 在通信工程 IDC/机房设备扩容场景已有实践。声明式设计覆盖了机柜、配电、暖通、布线四个系统的标准组件库。CI/CD 静态检查规则覆盖了约 30 条规范条款。工程产出从"图纸+计算书+邮件"变为"声明文件 + 编译产物 + CI 报告"。方案评审从会议室里的模糊判断变为 PR diff 里的精确对比。

但仍处于早期。组件库覆盖范围有限——非常规设备仍需手动定义 primitive。降阶模型的精度需要标注——不能让人误以为它是有限元。多人并发下的目录冲突处理策略仍在迭代。

---

> **Engineering as Code 的核心主张不是"用软件做工程"，而是——工程设计的知识应该以代码的形式存在、以 CI 的形式强制执行、以版本树的形式演化。** 当一条规范条款从"推荐"变成"可执行检查"的那一刻，它就从一个文本变成了一个制度。
