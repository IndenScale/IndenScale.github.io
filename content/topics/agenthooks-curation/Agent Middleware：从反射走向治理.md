## 引言：从 Layer 到 Level

当前 AgentHooks 的应用讨论往往陷入一个误区：将不同复杂度的使用方式视为**分层架构**（Layered Architecture），暗示它们应该堆叠使用。实际上，它们代表的是**成熟度等级**（Maturity Levels）——从简单的刺激-响应到系统性的生态治理。

本文提出 AgentHooks 应用的**三级成熟度模型**：

| 等级    | 名称                     | 核心特征            | 类比         |
| ------- | ------------------------ | ------------------- | ------------ |
| Level 1 | **反射级**（Reflex）     | 刺激-响应，正则匹配 | 生物反射弧   |
| Level 2 | **策略级**（Strategy）   | 环境感知，动态决策  | 战场战术     |
| Level 3 | **治理级**（Governance） | 生态补缺，系统治理  | 城市基础设施 |

这三级并非上下堆叠，而是**复杂度递进**——每一级解决不同难度的问题，组织可以根据自身需求选择合适的成熟度等级。

---

## Level 1：反射级（Reflex）

### 核心特征

反射级是 AgentHooks 最基础的使用方式，其特征类似生物的**反射弧**：

```text
事件刺激 → 模式匹配 → 固定响应
```

**关键属性：**

- **无状态**：每个事件独立处理，不维护跨事件上下文
- **确定性**：相同输入必然产生相同输出
- **局部性**：决策不依赖外部信息，仅基于事件本身

### 典型模式

**模式 A：危险命令阻断**

```yaml
# HOOK.md
trigger: pre-tool-call
matcher:
  tool: "Shell"
  pattern: "rm\s+-rf\s+/|mkfs|dd\s+if=/dev/zero"
---
# 脚本：直接阻断，无需查询环境
echo "危险命令被拦截" >&2
exit 2
```

**模式 B：简单通知**

```yaml
# PostToolUse 后发送 Slack 通知
# 播放提示音告知用户操作完成
# 发送邮件摘要
```

**模式 C：硬编码授权**

```yaml
# 特定目录需要确认
matcher:
  tool: "Write"
  pattern: "/etc/.*|/var/www/.*"
---
# 直接触发确认流程
```

### 适用场景

- 明确的安全红线（删除根目录、格式化磁盘）
- 简单的审计日志记录
- 不需要上下文的一次性确认

### 局限性

反射级无法处理**上下文相关**的决策：

- 无法判断 "删除 `node_modules`" 是否合理
- 无法区分 "main 分支提交" 和 "feature 分支提交"
- 无法理解 "当前处于什么阶段"

## Level 2：策略级（Strategy）

### 核心特征

策略级引入**环境感知能力**，使 Hooks 能够基于实时情境做动态决策：

```text
事件刺激 → 查询环境 → 情境分析 → 动态响应
```

**关键属性：**

- **情境感知**：主动查询 git 状态、文件系统、API 等
- **临时状态**：可维护会话级状态（如剩余预算）
- **动态决策**：相同输入在不同情境下可能产生不同输出

### 典型模式

**场景：分支敏感的提交策略**

```bash
#!/bin/bash
# pre-tool-call hook for "Git" tool

event_data=$(cat)
tool_input=$(echo "$event_data" | jq -r '.tool_input')

# 查询环境：当前分支
branch=$(git rev-parse --abbrev-ref HEAD)

# 查询环境：提交信息
commit_msg=$(echo "$tool_input" | grep -oP 'commit\s+\K.*')

# 策略决策
if [[ "$branch" == "main" ]] && [[ ! "$commit_msg" =~ ^(hotfix|release): ]];
then
  echo '{
    "decision": "deny",
    "error": {
      "code": "DIRECT_MAIN_COMMIT",
      "message": "禁止直接向 main 分支提交",
      "suggestion": "请创建 feature 分支: git checkout -b feature/xxx"
    }
  }'
  echo "当前分支: $branch, 提交被拒绝" >&2
  exit 2
fi

echo '{"decision": "allow"}'
exit 0
```

**场景：资源预算预警**

```yaml
# 维护会话级 token 消耗状态
# 在临界点提供优化建议
# 根据已消耗量调整建议策略
```

**场景：错误模式预防**

```yaml
# 查询测试历史
# 如果发现某类操作反复失败
# 在类似情境即将发生时提供预防性指导
```

### 与反射级的本质区别

| 维度         | 反射级         | 策略级             |
| ------------ | -------------- | ------------------ |
| **决策依据** | 事件本身       | 事件 + 环境查询    |
| **状态管理** | 无状态         | 临时状态（内存）   |
| **响应特性** | 固定           | 动态情境依赖       |
| **复杂度**   | 低（正则即可） | 中（需要脚本逻辑） |

### 局限性

策略级假设**环境提供了决策所需的全部信息**。当环境中缺少关键元信息时（如当前处于 SDLC 哪个阶段），策略级无法做出正确决策。

## Level 3：治理级（Governance）

### 核心特征

治理级是 AgentHooks 的**产品化形态**，它认识到当前 Agent 生态的元信息基础设施缺失，并主动填补这一空白：

```text
事件刺激 → 查询环境 → 读取治理状态 → 综合决策 → 更新治理状态
```

**关键属性：**

- **生态补缺**：维护生态系统中缺失的元信息（阶段、意图、历史）
- **持久状态**：跨会话保持上下文，长期累积
- **系统治理**：横切关注点分离，可组合的治理架构

### 核心问题：生态系统缺什么？

当前 Agent 工具链能提供的信息：

- Git 分支、提交历史、代码变更
- 文件系统状态、测试结果
- 环境变量、配置参数

**但无法提供的关键信息：**

- Agent 当前处于 **规划-构建-测试-发布** 哪个阶段
- 本次会话的原始意图和待办事项
- 已尝试方案的历史记录及结果
- 跨会话累积的上下文摘要

### 治理级作为补缺层

```text
决策输入 = 环境实时信息（git、文件系统、API）
        + 治理级维护的补充状态（阶段、意图、历史）
        ───────────────────────────────────────────────
        = 完整上下文
```

**关键原则：** 治理级不替代环境感知，而是与之互补——环境提供"客观现状"，治理级提供"主观上下文"。

### 典型模式

**场景：SDLC 阶段追踪与治理**

```yaml
# PreSession: 初始化治理状态
governance_state:
  session_id: "sess-abc123"
  original_intent: "重构认证模块以支持 OAuth"
  current_phase: "planning"  # planning → building → testing → review → release
  todo_items: ["更新 User 模型", "添加 OAuth 回调", "编写测试"]
  attempted_solutions: []
  remaining_blockers: []
  created_at: "2026-02-22T10:00:00Z"

# PreToolUse: 结合环境和治理状态做决策
logic:
  # 查询环境
  env_branch: "feature/auth-redesign"
  env_test_results: "FAILED"
  env_files_modified: ["src/auth.ts", "tests/auth.test.ts"]

  # 读取治理状态
  current_phase: "testing"
  remaining_blockers: ["集成测试环境问题"]

  # 综合决策
  if current_phase == "testing" && env_test_results == "FAILED":
    if "集成测试环境问题" in remaining_blockers:
      return {
        action: "suggest_promote",
        reason: "失败与已知环境问题相关，建议推进到代码审查阶段",
        guidance: "标记为 '环境相关失败'，准备 PR"
      }

# PostSession: 更新治理状态
governance_state_update:
  current_phase: "review"
  attempted_solutions: ["修复空指针", "更新 mock 数据", "绕过集成测试"]
  session_summary: "认证模块重构完成，待代码审查"
```

**场景：跨会话意图保持**

```yaml
# Session N: 建立意图
original_intent: "优化数据库查询性能"
sub_tasks: ["分析慢查询", "添加索引", "优化 ORM"]
completed: ["分析慢查询"]

# Session N+1: 恢复意图（可能是第二天，新会话）
restored_context:
  original_intent: "优化数据库查询性能"
  current_focus: "添加索引"
  previous_findings: "主要瓶颈在 user.posts 关联查询"

# Agent 启动时自动获得上下文，无需重新理解任务
```

### 横切关注点分离

治理级将 Agent 系统的关注点分离为可组合的模块：

```text
┌─────────────────────────────────────────────────────────┐
│                    业务逻辑层（Agent）                     │
├─────────────────────────────────────────────────────────┤
│  安全策略  │  合规审计  │  成本管控  │  质量门禁  │  可观测性  │
├─────────────────────────────────────────────────────────┤
│                    治理级基础设施                         │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐        │
│  │Security │ │Compliance│ │  Cost   │ │ Quality │  ...   │
│  │Governor │ │Governor  │ │Governor │ │Governor │       │
│  └─────────┘ └─────────┘ └─────────┘ └─────────┘        │
├─────────────────────────────────────────────────────────┤
│                    AgentHooks 事件层                      │
└─────────────────────────────────────────────────────────┘
```

每个 Governor 独立维护：

- **配置状态**：策略规则、阈值参数
- **运行时状态**：当前会话的上下文信息（阶段、意图）
- **历史状态**：跨会话的趋势数据
- **审计状态**：不可变的操作记录

### 部署模式

**模式一：本地治理（Development）**

```text
本地 Agent CLI → 本地 Governor 进程 → 本地状态存储（SQLite/JSON）
适用场景：个人开发、原型验证
特点：低延迟、简单调试、状态易失
```

**模式二：团队治理（Production）**

```text
Agent CLI ↔ 共享 Governor 服务 ↔ 团队状态存储（PostgreSQL/Redis）
适用场景：团队协作、统一治理
特点：跨会话状态共享、团队策略统一
```

**模式三：企业治理（Enterprise）**

```text
Agent CLI → API Gateway → Governor 服务集群 → 中央状态存储
                    ↓
              策略控制中心（Policy Control Plane）
适用场景：大规模企业部署、多租户环境
特点：集中策略管理、水平扩展、强审计
```

## 三级对比与选型

### 核心差异

| 维度         | 反射级       | 策略级                     | 治理级                   |
| ------------ | ------------ | -------------------------- | ------------------------ |
| **核心问题** | "这是什么？" | "基于现有信息，该做什么？" | "还缺什么信息？"         |
| **信息来源** | 事件数据     | 事件 + 环境查询            | 事件 + 环境 + 自维护状态 |
| **状态管理** | 无状态       | 临时状态（内存）           | 持久状态（跨会话）       |
| **决策特性** | 固定规则     | 动态情境依赖               | 系统性长期策略           |
| **产品形态** | 简单脚本     | 智能 Hook                  | Governor 基础设施        |
| **部署规模** | 个人         | 团队                       | 企业                     |

### 晋升阶梯的比喻

```text
反射级:    交通灯 → 红灯停，绿灯行
策略级:    交通灯 + 观察车流 → 判断是否可以通行
治理级:    交通灯 + 车流 + 目的地 + 历史路况 → 选择最优路线，长期优化城市交通
```

### 选型指南

**使用反射级当：**

- 规则明确且无歧义（`rm -rf /` 永远是危险的）
- 不需要上下文信息
- 快速部署，零维护成本

**使用策略级当：**

- 决策需要结合环境上下文
- 环境本身提供了足够的信息（git 状态、文件内容等）
- 需要动态响应，但不需要跨会话保持

**使用治理级当：**

- 环境中缺少关键的决策信息（如当前阶段）
- 需要维护 Agent 的长期状态（意图、历史尝试）
- 需要系统性治理多个横切关注点
- 需要跨会话保持上下文

### 关键信号

> **降级信号**：如果你在策略级反复计算相同的环境状态，那是信号——应该下沉为反射级的静态规则。

> **升级信号**：如果你发现策略级无法做出正确决策，因为"不知道 Agent 现在处于什么阶段"，那是信号——你需要治理级来维护缺失的信息。

> **越界信号**：如果你发现治理级变得过于复杂，试图重新实现环境感知（如自己解析 git 历史），那是信号——你正在越界，应该回到环境查询 + 状态补缺的组合模式。

## 演进路径建议

### 个人开发者

```text
起步阶段
└── 反射级（危险命令拦截）
    ↓
成长阶段
└── 策略级（分支保护、预算控制）
    ↓
（可选）进阶阶段
└── 轻量级治理级（本地 SQLite 维护阶段信息）
```

### 团队/组织

```text
初期
├── 反射级：安全红线
└── 策略级：分支策略、代码风格检查
    ↓
中期
└── 治理级引入：核心 Governor（安全 + 质量）
    ↓
成熟期
└── 完整治理基础设施：跨会话状态、团队策略中心
```

## 结论：选择适合的成熟度

AgentHooks 的三级成熟度模型不是竞争关系，而是**针对不同复杂度问题的分层解决方案**。

- **反射级**回答："基于固定规则，我该怎么做？"
- **策略级**回答："基于当前情境，我该怎么做？"
- **治理级**回答："基于系统性的信息和长期策略，我该怎么做？"

AgentHooks 的真正力量在于它**允许你在正确的成熟度等级上解决正确的问题**——从简单的刺激-响应，到环境感知，再到系统性的生态治理。
