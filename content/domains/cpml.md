## 施工计划是什么？

如果你问一个项目经理，他大概率打开一份甘特图。上面是几百条色条——每个色条代表一项活动，有开始时间、结束时间、前置依赖。

但这不是施工计划。这是施工计划的**可视化**。施工计划的本质是：

> 在给定的空间内、用给定的资源、在给定的时间窗口内、以给定的速率，完成一系列相互依赖的活动。并且——这一切在一个持续变化的环境中成立。

这里有四种约束：

- **空间约束**：两台吊车不能同时占同一个工作面的同一个高度。塔吊的覆盖范围是圆锥体——两个圆锥体的交集就是碰撞风险区。
- **资源约束**：灌浆料只够浇三个区段，第四段必须等。这不是"前置任务"——是产能排队。
- **时间约束**：经典的 FS（Finish-to-Start）、SS、FF、SF 依赖关系。A 完成 B 才能开始。
- **速率约束**：混凝土养护 7 天才能拆模。这不是一个"完成→开始"的布尔关系——它是一个**速率场**，随时间衰减。

现有工具没有一个能同时表达这四种约束。甘特图只能表达时间约束。BIM 只能表达空间约束。CPM 只能表达时间约束且假设每个活动的持续时间确定。

## 声明式 DSL 的设计

如果施工计划是一个可计算问题，那么它的语言应该是什么样的？

CPML 用 YAML 格式描述施工活动。核心概念：

- **Field**：一个可度量的物理量。crane_coverage（吊车覆盖）、concrete_maturity（混凝土成熟度）、space_occupancy（空间占用）。每个 Field 是一个随时间变化的标量场或向量场。
- **Activity**：一个施工活动。它有持续时间、占据的空间、消耗的资源、产出和需求。
- **Projection**：活动对 Field 的贡献——注入（开始占用）或提取（释放占用）。
- **Probe**：在某个时刻、某个位置对 Field 的采样——一个前置条件检查。

```yaml
activity:
  name: 吊装-区段A-钢结构
  structure: 区段A
  duration: 3d
  projections:
    - field: crane_coverage
      geometry: [[0,0,5], [50,20,25]]  # 塔吊覆盖的圆锥体
      presence: full                    # 全时段占用
    - field: space_occupancy
      geometry: [[0,0,0], [50,20,15]]  # 作业面
      presence: full
  probes:
    - field: concrete_maturity
      geometry: [[0,0,0], [50,20,15]]
      check: value >= 0.7              # 混凝土达到 70% 强度
```

当另一个活动 `吊装-区段B` 的覆盖范围与 `吊装-A` 在时间和空间上重叠时，编译器报冲突。

## 六阶段编译管线

CPML 编译器（Rust，约 4,000 行）执行六阶段管线：

1. **Parse**：YAML → 内部 IR
2. **Resolve**：符号解析——structure 名称、field 引用
3. **Expand**：语法糖展开。structure 自动生成占位检查、碰撞探测、遮挡检查
4. **Keyframe**：提取时间轴上所有活动开始/结束时刻，形成检查点序列
5. **Field Eval**：在每个 Keyframe 求值所有 Field 的状态——哪些空间被占、哪些资源被消耗
6. **Probe Check**：检查每个活动的所有 Probe 是否满足——不满足则报告冲突

碰撞检测使用 parry3d-f64 库的 GJK 算法做精确凸体碰撞。遮挡检测使用 raycasting——检查一个活动的工作面是否被另一个活动的几何体遮挡。

速率场带滑动窗口——混凝土养护的成熟度随时间连续变化，不是布尔量。FS/SS/FF/SF 四种经典依赖关系被编译为时间约束的 Probe。

`cpml compare` 支持多场景横向对比——同一份计划在两个不同施工顺序下的结果并排展示。

## 为什么编译到 WASM

CPML 编译到 WASM 不是为了"部署到 Web"——是为了**分发和沙箱**。

施工计划文件（.cpml）是纯文本 YAML，可以在任何地方编辑。编译器本身编译为 WASM 后，可以嵌入浏览器、嵌入飞书、嵌入 VS Code——不需要安装 Rust 工具链。项目经理在飞书里上传一份计划文件，浏览器里的 WASM 编译器跑完检查，返回诊断结果。

这是产品思考，不是技术炫技。

## 从哪里来

CPML 不是从教科书里推导出来的。它来自中卫项目现场的观察——甘特图在真实冲击面前的无力、BIM 模型躺在服务器里和施工计划没有可执行的连接、设备排队逻辑的缺失。

它目前的形态是一个 POC 编译器——15 个示例文件、14 个集成测试、Criterion 性能基准。它可以检查碰撞、争用和进度漂移。但它还不能做离散事件仿真——下一步是在 CPML 之上构建 DES + 蒙特卡洛引擎，回答"如果再来一次吊装事故，最优应对方案是什么"。
